LEARNING MODULE 04 · 問題解決力

分からない問題を、
解決できる問題に変える

正解を知っていることよりも、状況を整理し、根拠を積み重ねて解決に近づくことを目指します。

想定期間：2〜4週間学習時間：合計6〜10時間初級〜中級・調整可能

このモジュールの到達目標

未知の問題に直面したとき、事実と推測を区別し、仮説を立てて検証し、必要に応じて他者やAIの力も借りながら、根拠を持って解決策を判断できる。

基本的なIT操作・用語を想定しています。担当業務や経験に合わせて題材と支援の程度を調整できます。時間は目安です。

A · 知る

仮説検証と原因切り分けの基礎

問題解決の第一歩は、原因を思いつくことではなく、何が分かっていて何が分かっていないかを整理することです。

現象・問題・原因・解決策を分ける

概念ログイン障害での例
現象ログインするとエラーが表示される。
問題業務に必要なシステムにアクセスできない。
原因アクセスに必要な権限が割り当てられていなかった。
解決策権限の状態を確認し、承認後に適切な設定へ復旧する。

現象を確認した時点では、原因はまだ仮説です。パスワード、端末、ネットワーク、設定など複数の可能性を考えます。

事実と推測を分ける

問い合わせの例

「今朝ログインできません。昨日までは使えていたので、昨夜の更新が原因だと思います」

「今朝ログインできなかった」「昨日までは使えた」は利用者からの報告です。時刻や条件は追加の確認が必要かもしれません。「更新が原因」は未検証の仮説です。影響範囲など、分からないことは「不明」と記録します。

仮説を立て、検証する

  1. 情報を集める：エラー、発生時刻、影響範囲、環境、変更履歴を確認する。
  2. 候補を考える：得られた情報に合う原因を複数挙げ、影響や確認のしやすさを考えて優先する。
  3. 検証を設計する：何を確認し、どの結果なら仮説を支持・見直せるかを決める。
  4. 結果から更新する：確認できたことと、まだ言えないことを分け、次の調査を決める。
  5. 対応を判断する：暫定・恒久対応の効果とリスクを比べ、必要な承認、影響、戻し方と復旧確認を整理する。

たとえば一人だけ失敗しても、アカウントの問題とは限りません。端末やブラウザの違いも候補に残り、追加の確認が必要です。

AIと他者を活用する

AIには原因候補や検証方法、見落としへの指摘を求められます。ただし、回答自体は原因特定の証拠ではありません。公式資料や実際の観察結果で確かめましょう。外部AIに情報を入力する際は、会社・顧客の規程を確認し、個人情報・認証情報・機密情報を適切に扱います。解決できないときは、影響、確認済み事項、仮説、未解決事項を整理して適切な担当者に相談します。

B · 試す

演習：社内システムにログインできない

目安：90〜120分 · 架空のシステムとデータを使用

問い合わせ

午前9時、営業部の社員から「今朝から勤怠管理システムにログインできません。昨日までは普通に使えていました」と連絡がありました。システムは社内ネットワーク上のWebアプリで、会社の共通アカウントを使います。

取り組み方

  1. 現象を整理：最初に確認したい事項と、それぞれの確認で何を判断するかを書き出す。
  2. 情報を収集：指導者に質問し、得られた情報を事実・報告・不明点に分ける。
  3. 仮説を検証：原因候補を3つ程度挙げ、それぞれの根拠、確認方法、予想される結果を整理する。
  4. 対応を検討：証拠から結論の確度を判断し、暫定・恒久対応、承認、影響、戻し方、復旧確認を考える。
  5. 報告：問い合わせ元には状況を分かりやすく伝え、管理者には証拠・影響・対応方針を報告する。

最初の15〜20分は、以下の情報を見ずに調査方針を考え、その後に基礎教材を読んでから演習を進める方法もあります。事前と事後の考え方を比較しましょう。実施者がすでにこのケースの答えを知っている場合は、指導者が別の原因パターンを用意してください。

指導者向け：追加情報カード

以下は演習用に具体化した架空の情報です。関連する質問や確認が出たときに、指導者が一つずつ提示してください。受講者は必要になるまで開かないようにしましょう。

エラー内容を確認する

共通アカウントの入力後、勤怠管理システムに「アクセスできません。管理者にお問い合わせください」と表示される。詳細なエラーコードは画面に表示されない。

他の社員への影響を確認する

営業部の同じグループに所属する別の社員も同様のエラーになる。他部署の確認済みの社員はログインできる。全体の影響範囲はまだ調査中。

他のシステムを確認する

対象社員は同じ共通アカウントで別の社内システムにログインできる。

端末・ブラウザを確認する

対象社員は別の確認済み端末と別のブラウザでも同じエラーになる。これだけで端末に関するすべての可能性を否定できるわけではない。

最近の変更を確認する

前夜に勤怠管理システムの認証関連設定が更新されていた。更新と障害の因果関係は、この情報だけでは確定しない。

ログを確認する

管理者が確認したアプリのログでは、対象社員の認証は成功しているが、その後の認可処理で必要なロールがないため拒否された記録がある。

アカウントと権限を確認する

対象アカウントは有効で、対象社員は所定の営業部グループに所属している。一方、勤怠管理システムが必要とするロールは付与されていない。

設定変更の差分を確認する

更新前は営業部グループが勤怠管理システムの必要なロールに対応していたが、更新後の設定ではその対応が外れている。

指導者向け：想定解答と対応の観点

設定更新後に営業部グループと必要なロールの対応が外れ、認証後の認可処理でアクセスが拒否されたと考えられます。ログ、グループ所属、設定差分を根拠にし、未確認の影響範囲は明示します。設定修正とロールバックを比較し、権限・承認・他の利用者への影響・戻し方・復旧確認を検討します。再発防止として変更時の影響確認や認可テストの追加を提案できます。

提出物：確認事項、仮説と検証結果、対応方針をまとめた調査レポートと、問い合わせ元・管理者それぞれに向けた報告。正解だけでなく、判断の根拠と受けた支援を残します。

C · 使う

実務チャレンジ：問い合わせを調査して報告する

実際の問い合わせや障害を一件選び、事実の整理、仮説、検証、判断を記録します。動作が遅い、Excelの計算結果がおかしい、業務手順が分からないといった題材でも構いません。

  1. 問い合わせと影響範囲、緊急度を確認する。
  2. 確認できた事実、利用者の報告、推測、不明点を分ける。
  3. 原因候補と確認方法を整理し、結果に応じて仮説を更新する。
  4. 未解決事項を明示し、必要に応じて適切な担当者に相談する。
  5. 対応の効果とリスクを比べ、関係者に報告する。
実務での前提

本番環境の変更前に権限・承認・影響・戻し方を確認します。個人情報や認証情報は適切に扱い、重大障害やセキュリティ事故では組織の対応手順を優先してください。

問題調査レポートの項目

  • 問い合わせ概要：内容、日時、対象、影響範囲、緊急度と理由。
  • 情報の整理：確認できた事実、利用者の報告、不明なこと。
  • 仮説と検証：原因候補、根拠、確認方法、調査日時、結果と分かったこと。
  • 結論：原因の確度（確定・有力・未特定）、裏付け、未確認事項。
  • 対応方針：暫定・恒久対応、影響とリスク、必要な承認・協力、戻し方と復旧確認。
  • 再発防止と振り返り：改善案、AIや外部資料の利用と検証方法、うまくいったこと、次回の改善。

提出物は調査レポートと振り返りシートです。初級者は過去の既知の問い合わせを指導者と調べることから始められます。経験に応じて現在の問題や複数要因のある問題へ進みます。

D · 身につける

振り返り・評価

原因を特定できたかだけでなく、調査の進め方と支援の程度を評価します。未解決でも、影響を把握し、根拠を整理して適切に相談することは前進です。

評価の目安

1：進め方に支援が必要、2：支援を受けて実行、3：自分で実行、4：状況に応じて見直し・改善を目安に、具体的な行動と受けた支援を記録します。すべてでレベル4を目指す必要はありません。

観点確認する行動の例
状況整理事実・推測・不明点を分け、影響範囲と優先度を整理する。
仮説立案根拠に基づき複数の候補を挙げ、確認の順番を考える。
検証仮説に対応する確認を行い、結果に応じて方針を見直す。
解決策の判断暫定・恒久対応の効果やリスクを比較する。
相談・報告相手が次の判断をできるよう、状況と必要な協力を伝える。

振り返りの5問

  1. 最初に考えた原因候補と、それを疑った理由は何ですか？
  2. 新しい情報によって、最初の考えが変わった場面はありましたか？
  3. 最も有効だった確認・検証は何でしたか？
  4. 自分で解決できなかったことに、どう相談・対処しましたか？
  5. 次に似た問題が起きたら、調査方法をどう改善しますか？

診断と次の実践へ

診断の「問題解決力」にある、事実と推測の整理、仮説検証、解決策の比較、適切な相談を、調査記録と照らして振り返りましょう。演習の完了だけで評価を上げるのではなく、別の実務場面でも再現できるか確認します。
