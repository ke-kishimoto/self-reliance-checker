LEARNING MODULE 05 · 技術実践力

「作れる」から
「安心して使えるものを作れる」へ

技術を使って業務上の問題を解決し、成果物を安全に使い続けるための設計・実装・テストを経験します。

想定期間：3〜5週間学習時間：合計10〜16時間初級〜中級・調整可能

このモジュールの到達目標

業務上の課題に対して適切な技術を選び、要件を整理したうえで設計・実装・テストを行い、安全性・保守性・運用を考慮した成果物を提供できる。

基本的なPC操作とプログラミングの初歩を想定しています。時間は基礎的な開発経験がある人向けの目安です。未経験者は言語や開発環境の入門学習を別途行い、支援や課題の範囲を調整してください。

A · 知る

設計・実装・テストの基本

開発を始める前に、何を解決したいか、既存の仕組みで何が不足しているか、開発以外の選択肢はないかを考えます。頻度、変更ミスのリスク、監査性、開発・運用の負担を比べ、作るべきかを判断しましょう。

要件と完成条件を整理する

利用者と権限

誰が参照・変更できるか。

データと業務ルール

何を扱い、必須入力や重複禁止などの条件は何か。

制約と品質

利用環境、データ保護、エラー時の扱いなど、守るべき条件は何か。

完成条件

どの動作や確認ができれば完了とするか。

曖昧な条件は関係者に確認し、決まった内容からテストの観点を考えます。

変更しやすく設計し、小さく作る

画面・入力、業務ルール、データ保存のそれぞれが何を担当するか考えます。これは責務を整理するための例で、必ず特定の構成を採用する必要はありません。小さく実装して動作確認し、改善するサイクルを繰り返しましょう。AIが生成したコードも役割を理解し、確認とテストを行ってから使います。

動作を確かめ、運用まで考える

正常な入力だけでなく、未入力・重複・不正な値などの異常系、最大文字数などの境界値、修正によって以前の機能が壊れていないかという回帰も確認します。想定する権限、データ保護、バックアップ、エラー時の対応、変更履歴、リリースや保守の手順を整理し、残った制約を利用者に伝えます。

B · 試す

演習：商品マスタの管理機能を作ろう

目安：5〜8時間 · 架空の業務とデータを使用

課題シナリオ

商品マスタをExcelで直接編集している会社で、入力ミスや重複登録が発生しています。商品情報を管理する小さな仕組みを作り、設計からテストまでの過程を記録してください。

必須要件

  • 商品の一覧を表示し、新規登録と登録済み商品の変更ができる。
  • 商品コードの重複を拒否し、必須項目が未入力ならエラーを表示する。
  • 登録・変更した情報が永続的に保存される。

商品コードの形式、商品名の文字数、価格の範囲、コード変更や削除の可否、利用者の権限などは課題文だけでは決まっていません。指導者や依頼者に確認し、合意した条件を要件とテストに反映してください。

進め方と成果物

  1. 要件整理：不明点を確認し、業務ルールと完成条件を要件メモにまとめる。
  2. 設計：商品コード・商品名・価格などのデータ、画面、処理の責務を簡易設計書にまとめる。
  3. テスト設計：実装前に入力、操作、期待結果をテストケース一覧に記録する。
  4. 実装：一覧、登録、入力チェック、更新を小さく作り、都度確認する。AIの利用箇所も記録する。
  5. テストと改善：期待結果と実行結果を比較し、不具合や指摘を修正する。ソースコード、テスト結果、改善後の成果物を提出する。

テストケースの例

確認する操作期待する結果
正しい商品情報を登録する登録され、一覧に表示される。
必須項目を空にする、または商品コードを重複させる登録されず、理由を確認できる。
不正な価格や合意した文字数を超える値を入力する定めたルールに従って拒否される。
登録済みの商品を変更する変更が保存され、再起動後も残る。
存在しない商品を更新する変更されず、適切なエラーになる。

権限制御を実装する場合は、権限のない利用者の変更が拒否されることも確認します。自動テストは必須ではありません。テストできていない条件も記録しましょう。

経験に合わせた調整

初級：Accessのテーブル・フォームなどを使い、入力チェックの基本を学ぶ。
中級：Webアプリで管理機能を作り、画面、業務ルール、保存の責務を考える。
発展：検索、無効化、更新履歴、権限制御、自動テストなどから必要なものを追加し、保守性を検討する。

使用技術は統一せず、同じ目的と評価観点で取り組みます。架空データを用いた演習用の実装を、そのまま本番で安全に使えるものと見なさないでください。

C · 使う

実務チャレンジ：定型作業をツール化する

目安：5〜10時間

担当業務の定型作業を一つ選び、1〜2週間程度で取り組める小さな範囲のツールを作ります。CSVの形式チェック、Excelの集計、帳票作成などを題材に、現行方式と正確性・安全性・効率・保守性を比較しましょう。開発以外の方法が適切なら、その判断も記録します。

  1. 対象業務、現状の問題、解決したいことを確認する。
  2. 利用者、入力・出力、業務ルール、権限、完成条件を決める。
  3. 技術を選び、小さく設計・実装し、正常系と異常系をテストする。
  4. 既存データへの影響を確認し、利用手順とエラー時の対応を残す。
  5. 改善前後の負担や正確性、残ったリスク、利用者の意見を記録する。
実務での前提

まずは検証環境と適切に加工されたテストデータを使用し、本番データを直接操作しません。実運用を始める場合は、業務責任者や指導者のレビューと承認を受けてください。検証用ツールの完成まででも学習成果になります。

ツール化レポートの項目

  • 対象と目的：現在の作業方法、問題、解決したいこと。
  • 要件・設計：利用者、機能、データ、ルール、安全上の注意、完成条件、技術選定の理由と処理の流れ。
  • 実装：実装した機能、工夫、AIの利用箇所、発生した問題と対応。
  • テスト：ケースごとの入力・操作、期待結果、実行結果、未確認事項。
  • 評価：改善前後の時間や負担、正確性、利用者の意見、残る問題とリスク。
  • 運用・保守と振り返り：利用手順、問い合わせ先、エラー時の対応、改善候補、学んだこと。

D · 身につける

振り返り・評価

動く成果物だけでなく、要件の確認、設計上の判断、テストで発見した問題、改善の過程を評価します。完成しなかった機能や支援を受けた箇所も明らかにします。

評価の目安

1：進め方に支援が必要、2：支援を受けて実行、3：自分で実行、4：変更や運用を踏まえて改善を目安に、具体的な行動と支援の内容を記録します。全員がレベル4を目指す必要はありません。

観点確認する行動の例
要件整理必要な機能、完成条件、制約や運用を整理する。
設計データ構造と処理の責務を考え、変更・保守のしやすさを検討する。
実装調査やAIを活用しながら機能を作り、その内容を説明する。
テスト正常系・異常系を設計して実施し、必要に応じて回帰も確認する。
運用・保守他者が利用・保守するための手順や安全な運用を考える。

振り返りの5問

  1. 作ったものは、どのような問題を解決するためのものですか？
  2. 設計・実装で迷ったことと、判断した理由は何ですか？
  3. テストによって発見した問題は何ですか？
  4. 仕様変更が入るとしたら、どこを修正する必要がありますか？
  5. 他の人が利用・保守するために、何を改善したいですか？

診断と次の実践へ

診断の「技術実践力」にある、技術選択、調査・AIを活用した実装、動作検証、保守性・安全性・運用への配慮を、成果物と記録から振り返ります。演習の完了だけで習得を判断せず、別の小さな開発課題でも実践できるか確認しましょう。
